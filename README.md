# askin

내가 Claude Code 를 어떻게 쓰고 있는지 점검하고, 어긋난 하네스를 그 자리에서 고치는 도구.

**대시보드가 아니라 개선 루프가 목적이다.** 실태를 알아도 고치는 게 손이면 절반이다.

제품 이름은 askin 이다. `harness-bro` 는 디렉터리 이름이고, 이 저장소가 자기 자신을
분석 대상으로 부를 때 쓰는 프로젝트 이름이기도 하다. 제품명은 아니다.

왜 이렇게 재는지는 `CLAUDE.md` 의 재는 규율과 판정의 결에 있다. 화면 설계는
[`desktop/design-concept.md`](desktop/design-concept.md) 와 [`desktop/wireframe.md`](desktop/wireframe.md) 다.

## 쓰기

```bash
node src/report.mjs                    # 현재 디렉터리를 저장소로 보고
node src/report.mjs --repo <경로>
node src/report.mjs --all              # 전 프로젝트 (저장소 축은 건너뜀)
node src/report.mjs --since 2026-07-27 --until 2026-08-26T06:00
node src/report.mjs --all-time         # 전체 기간 (기본은 최근 30일)
node src/report.mjs --save             # 이번 집계를 스냅샷으로 쌓는다
node src/report.mjs --html out.html    # 한 장으로 그린다
node src/report.mjs --plan             # 고칠 것을 갈래로 갈라 지시서로 뽑는다
node src/report.mjs --json             # 스크립트로 쓸 때. 아래 참고
node src/report.mjs --no-cache         # 캐시 없이 전부 다시 읽는다
node src/report.mjs --watch            # 상주. 나빠진 것만 말한다
npm test
```

전 프로젝트 기준으로 전사 1,266개(1.03GB)에서 위임 1,108건과 세션 152개를 훑는다.
처음 4.3초, 그다음부터 **0.08초**다.

전사 파일은 append-only 라 한 번 쓰인 줄이 안 바뀐다. 그래서 파일에서 뽑은 사실을
크기+mtime 으로 캐시하고 바뀐 파일만 다시 읽는다. 실측으로 최근 1분에 바뀐 파일이 1개다.

전사를 하드링크로 복제해 커지는 하네스를 재봤다. **선형 이하다.**

| 전사 | 첫 실행 | 캐시 | 캐시 크기 |
|---|---|---|---|
| 1,225개 | 4.7초 | 0.09초 | 2.3MB |
| 4,900개 | 12.5초 | 0.25초 | 9.2MB |
| 9,800개 | 25.8초 | 0.48초 | 18.8MB |

파일이 8배가 되면 첫 실행이 5.5배, 캐시 실행이 5.3배다. 캐시 크기만 파일 수에
선형으로 는다. 두 주 안 만진 캐시 파일은 스스로 걷는다.
캐시는 `~/.harness-bro/cache/` 에 있고 지워도 답은 같다. 느려질 뿐이다.
파일은 보는 뿌리마다 갈라 두고, 두 주 동안 안 만진 것은 스스로 걷는다.

### 창의 경계

`--since` 는 **포함**이고 `--until` 은 **배제**다. `[since, until)` 이다.
8월 1일 하루를 보려면 다음 날을 준다.

```bash
node src/report.mjs --all --since 2026-08-01 --until 2026-08-02   # 8월 1일 하루
```

**세션은 창과 겹치면 잡는다.** 위임은 시점 하나로 판단하는데 세션은 기간이라 그렇다.
그런데 세션 기반 축(훅 무결성·가드 차단·위임률·캐시 적중률)의 집계는 세션 **전체 기간**
값이라 창으로 안 잘린다. 그래서 리포트가 얼마나 넘치는지 말한다.

```
위임 4건 (전체 1067건 중), 세션 14개
※ 세션 14개 중 14개가 이 창 밖으로 뻗는다. 훅·차단·턴 표본의 100% 가 창 밖 값이다
```

창이 짧을수록 심하다. 실측으로 하루 창은 100%, 한 주 87%, 30일 25% 였다.
**짧은 창에서는 세션 기반 축을 믿지 마라.** 위임 기반 축(모델 명시·잡무 모델)은
시점으로 자르니 창을 지킨다.

### `--json` 으로 게이트를 걸 때

**판정된 축과 못 잰 축이 구조로 갈려 있다.** `compliance` 와 `observation` 에는 잰
것만 들어가고, 못 잰 것은 `unjudged` 로 나온다.

```bash
# 준수율 95% 아래를 찾는다. 판정 불가는 안 걸린다
node src/report.mjs --json | jq -r '.compliance[] | select(.rate < 0.95) | .id'

# 왜 못 쟀는지 본다
node src/report.mjs --json | jq -r '.unjudged[] | "\(.id) — \(.why)"'
```

가르지 않으면 `jq` 에서 `null < 0.95` 가 참이라 **"위임 기록이 없다"가 "준수율 미달"로
잡힌다.** 실측에서 판정 불가 3건이 그렇게 걸렸다.

## 무엇을 보나

| 파일 | 원천 | 한 줄이 무엇인가 |
|---|---|---|
| `src/scan.mjs` | `~/.claude/projects` 전사 | 위임 한 건, 세션 한 개 |
| `src/refs.mjs` | 파일 시스템 | 에이전트 정의, 선언된 스킬, 문서가 가리키는 경로 |
| `src/contradictions.mjs` | 하네스 문서 | 두 문서가 반대로 말하는 토큰 |
| `src/axes.mjs` | — | 판정 축 |
| `src/report.mjs` | — | 축을 사실에 적용 |
| `src/snapshot.mjs` | — | 시점별 집계 |
| `src/render.mjs` | — | 한 장짜리 화면 |
| `src/filecache.mjs` | — | 안 바뀐 파일은 다시 안 읽기 |
| `src/watch.mjs` | — | 자라면 다시 재고 나빠진 것만 말하기 |
| `src/series.mjs` | — | 주별 추세 |
| `src/fix.mjs` | — | 고칠 것을 겹치지 않는 갈래로 |
| `scan-rs/` | — | 세션 전사를 읽는 Rust 스캐너. `--scanner rust` 로 쓴다 |
| `tools/facts.mjs` | — | 뽑는 층이 내는 사실을 파일 한 줄씩 찍는다 |
| `tools/compare.mjs` | — | 스캐너 둘이 같은 답을 내는지 견준다 |

**축이 판정을 독점한다.** `scan.mjs` 와 `refs.mjs` 는 비율을 계산하지 않는다.
측정 함정이 집계 코드에 박히면 축을 하나 더 만들 때 같은 함정을 다시 밟는다.

뽑는 층은 갈아끼울 수 있다. `readSession` 과 `extractFile` 이 파일 하나에서 사실을 내는
전부라서, 그 둘만 다른 말로 다시 쓰면 판정 층은 그대로 둔 채 바꿀 수 있다.
바꾸기 전에 `tools/compare.mjs` 로 같은 답을 내는지 먼저 본다.

```bash
node tools/facts.mjs > js1.ndjson
<새 스캐너>          > new.ndjson
node tools/facts.mjs > js2.ndjson
node tools/compare.mjs js1.ndjson new.ndjson js2.ndjson
```

**전사는 지금도 자란다.** JS 를 앞뒤로 두 번 찍어 그 사이에 안 자란 것만 견준다.
실측(2026-08-28): 5초 사이에 1,254개 중 1개가 자랐고, 그게 지금 도는 세션의 전사였다.

**키 순서까지 같아야 한다.** 훅은 처음 나온 순서로 담기고 그 순서가 리포트의 사례 순서가 된다.
정렬해서 견주면 "같다"가 나오는데 화면의 사례 순서가 다르다. 실제로 그렇게 놓쳤다.

세션 전사를 읽는 Rust 스캐너가 `scan-rs/` 에 있다. 먼저 빌드해야 쓴다.

```bash
cd scan-rs && cargo build --release
node src/report.mjs --all --scanner rust
```

**캐시에 없는 파일만 넘긴다.** 늘 부르면 캐시가 맞을 때 오히려 느려진다.
캐시 지문에 바이너리의 크기와 mtime 이 들어가서, 다시 빌드하면 옛 캐시를 안 쓴다.

뽑는 함수 셋(`readDelegation`·`readSession`·`extractFile`)을 다 Rust 가 읽는다.

| 전 프로젝트 리포트, 캐시 없이 | |
|---|---|
| JS | 3,147ms / 2,951ms |
| `--scanner rust` | **645ms / 715ms** |

한 프로세스에서 디스크를 데운 뒤 번갈아 잰 값이다. **CLI 를 밖에서 재면 안 된다.**
차가운 디스크가 차이를 덮어서 3~5초 사이로 흔들린다. 같은 답을 내는지는 매번 확인한다
(위임 888건, 세션 139개로 둘이 같다).

캐시가 맞으면 둘 다 0.1초 아래다. 스캐너를 아예 안 부르기 때문이다.

기본 축은 `src/axes.mjs` 에 있고, `~/.harness-bro/axes.mjs` 를 두면 거기서 더하거나 끌 수 있다.
`HARNESS_BRO_AXES` 로 경로를 바꿀 수 있다.

```js
// ~/.harness-bro/axes.mjs
export const compliance = [
  { id: 'no-deep-nesting', label: '위임 깊이', rule: '내 규칙: 두 단계 넘게 겹치지 않는다',
    source: 'delegations', scope: (r) => r.spawnDepth != null, violation: (r) => r.spawnDepth > 2 },
]
export const disable = ['chore-model']   // 기본 축 끄기
```

**축 정의 문법을 새로 만들지 않았다.** 내 기계에서 내가 쓰는 도구라 JS 모듈이면 충분하다.
규칙이 바뀌면 앱이 아니라 이 파일만 고친다.

**축 파일이 깨져 있으면 조용히 넘어가지 않는다.** 그냥 기본으로 돌아가면
사용자는 자기 축이 도는 줄 안다. 무엇이 왜 안 읽혔는지 말하고 기본으로 돈다.

**id 는 준수율과 관찰값을 가로질러 전역이다.** 스냅샷과 주별 추세가 id 로만 축을 찾는다.
겹치는 id 로 축을 얹으면 그 축을 빼고 말한다. 기본 축을 바꾸려면 `disable` 로 끈 다음
같은 id 를 다시 쓰면 된다. 기본 축이 먼저 자리를 잡으니 오타 하나로 기본 축이 사라지지 않는다.

## 판정 축 두 종류

섞지 않는다.

- **준수율**: 기준이 이미 내가 쓴 규칙이다. 목표는 100%
- **관찰값**: "얼마가 좋은가"의 기준이 없다. 추세로만 본다

**종합 점수는 만들지 않는다.** 왜 떨어졌는지를 가린다.
대신 위반이 어디에 몰렸는지를 건수와 분모로 같이 보여준다.

**프로젝트를 가로질러 평균 내지도 않는다.** 실측에서 가중 평균 97.6%, 프로젝트마다
한 표씩이면 87.7% 로 10%p 가 벌어졌다. 어느 쪽을 골라도 korean-tone 이 85% 라는 사실이 가려진다.
전 프로젝트를 볼 때는 프로젝트별로, 한 저장소를 볼 때는 에이전트 타입별로 묶는다.

**표본이 없으면 0% 가 아니라 판정 불가다.** 데이터가 없는 것과 규칙을 안 지킨 것은 다르다.
분모가 빈 축은 예외 없이 왜 못 재는지 말한다. "0건 중 0건 위반"은 도구가 고장난 건지
데이터가 없는 건지 알려주지 않는다.

**준수율의 기본 창은 최근 30일이다.** 목표가 100% 인 축을 전체 기간으로 재면
과거를 못 고치니 영원히 100% 로 못 돌아온다. 도달 불가능한 목표는 고치는 루프를 깬다.
실측으로 모델 명시가 전체 기간 94.8%, 최근 30일 97.6%, 최근 14일 99.3% 였다.
위반 53건 중 대부분이 7월이라 옛 잔재가 점수를 눌렀다.

**"지금은 지키고 있다"는 관찰은 틀렸다.** 2026-08-27 에 다시 재보니 위반이 7월 12건,
8월 9건으로 줄기만 하고 멈추지 않았다. 마지막 위반이 그날 아침이다. 창을 좁히는 근거는
"과거를 못 고치니 도달 불가능한 목표가 된다"이지 "이제 다 지킨다"가 아니다.

기간 창은 추세를 비교할 때 범위의 일부로 친다. 최근 30일치와 전체 기간치를 섞으면
`--all-time` 한 번이 추세에 절벽을 만들고 그게 실제 변화처럼 보인다.

화면에서도 둘을 다르게 그린다. 준수율은 목표가 100% 라 100 을 기준으로 게이지를 그리고,
관찰값은 목표가 없어서 지나온 값의 범위 안에서만 추세를 그린다.

**추세는 스냅샷이 아니라 데이터에서 주 단위로 뽑는다.** 스냅샷은 `--save` 를 돌린 시점에만
생겨서 시간 간격이 거짓말한다. 위임에는 줄마다 `ts` 가 있으니 소급해서 진짜 시계열이 나온다.
일 단위는 분모 2인 칸이 생겨 못 쓰고, 30일 이동창은 연속한 두 점이 29일을 공유해 너무 매끄럽다.
**분모가 20건 미만인 칸은 비율을 안 낸다.**

## 고치는 쪽

**앱이 Claude Code 를 대신하지 않는다.** 기계가 정확히 할 수 있는 두 가지만 한다.

1. 어느 파일을 건드려야 하는지 모으는 것
2. 파일이 겹치지 않는 갈래로 가르는 것

2번이 `src/fix.mjs` 의 이유다. 손으로 가르면 겹치는 것을 놓치고
같은 파일을 두 에이전트가 동시에 고친다. 겹침은 전이적이라 눈으로 따라가기 어렵다.

`--plan` 이 갈래마다 지시서를 뽑는다. 지시서에는 다른 갈래가 건드리는 파일 목록과
"읽기만 하라", 거부 조건, 끝나고 돌릴 검증 명령이 들어간다.

**모순 후보가 섞인 갈래는 지시서가 먼저 그렇게 말한다.** 기계는 후보만 좁혔으니
실제로 어긋나는지 읽고 판단하고, 아니면 고치지 말고 보고하라고 못박는다.
근거가 사라진 축도 같다. 규칙을 일부러 바꿨으면 축을 고치고 실수로 지웠으면 문서를
고치는데, 어느 쪽인지는 기계가 못 고른다.

갈래로 나오는 것은 리포트가 찾은 것 전부다. 죽은 경로, 없는 스킬 선언,
스킬 디렉터리의 깨진 심링크, 근거가 사라진 축, 모순 후보. **하나라도 빠지면
`--plan` 이 "깨끗하다"고 거짓말한다.**

## 상주할 때는 나빠진 것만 말한다

알림의 실패 모드는 두 가지고 방향이 반대다. 너무 말이 많으면 아무도 안 보고,
너무 없으면 있으나 마나다. 선은 **준수율이 떨어지거나 죽은 자산이 생기면**이다.

좋아진 것은 스냅샷에만 조용히 쌓는다. 말하면 알림이 축하 인사로 변한다.
반올림해서 같아 보이는 흔들림도 말하지 않는다.

## 안전 불변식

**앱은 `~/.claude/projects` 를 절대 쓰지 않는다.** 읽기만 한다.
점검 도구가 점검 대상을 지우면 사고가 났을 때 되돌릴 방법이 없다.

이 앱이 쓰는 곳은 `~/.harness-bro/snapshots.jsonl` 하나다.
`HARNESS_BRO_STORE` 로 바꿀 수 있다.

## 측정 함정

숫자가 거짓말하는 자리다. 전부 실측으로 확인했고 `test/` 에 고정해뒀다.

수치는 실측한 그때의 값이다. 전사가 자라고 정리되면서 숫자는 움직이지만 방향은 그대로다.
**번호는 소스 주석이 참조하니 재정렬하지 않는다.** 새로 찾은 것은 뒤에 붙인다.

1. **`fork` 를 모델 명시 분모에서 뺀다.** 정의상 부모 모델을 상속한다. 안 빼면 90.8%, 빼면 98.1%
2. **병렬은 `message.id` 로 묶는다.** 배열 길이로 세면 항상 1.00 이 나온다
3. **서브에이전트는 `meta.json` 으로만 센다.** 부모의 `tool_use` 블록이 자식 전사에 복사돼 있다
4. **세션 수에서 `subagents/` 를 뺀다.** 안 빼면 6~7배 부풀려진다
5. **`subagents/workflows/<wf-id>/` 도 읽는다.** 1,098건 중 81건이 거기 있다
6. **훅 성공을 `type` 의 "success" 로 가르지 않는다.** `hook_additional_context` 도 정상이다
7. **세션은 거쳐온 `cwd` 전부로 저장소에 잇는다.** 슬러그는 `/` 를 `-` 로 바꾼 것이라
   되돌릴 수 없고, 첫 `cwd` 만 잡으면 옮겨온 세션이 시작한 곳에 달린다
8. **임시 디렉터리는 프로젝트가 아니다.** `-private-tmp-` 같은 슬러그를 거른다
9. **서브에이전트 전사의 훅도 그 세션 것으로 센다.** 3·4번과 단위가 다르다.
   세션 수에서는 빼지만 그 안에서 돈 훅 실행은 세야 한다. `SubagentStart` 계열
   2,947건이 본 세션 전사에 하나도 없어서 아예 재지 않고 있었다
10. **서브에이전트에서 막힌 도구도 그 세션 차단으로 센다.** 차단의 44% 가 거기서 났다.
    턴(`turn_duration`)은 서브에이전트 전사에 없으니 분모는 본 세션 것만 센다
11. **`hook_cancelled` 은 사람이 취소한 게 아니라 시간 초과다.** `timedOut` 이 붙어 있다.
    잘린 훅은 규칙을 적용하지 못했으니 실패로 센다. `hook_system_message` 는 정상이다
